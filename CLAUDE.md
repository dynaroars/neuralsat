# NeuralSAT (minimal)

## Code style

- Functional programming only. Do not define any classes (no `class`,
  `@dataclass`, `NamedTuple` classes, `nn.Module` subclasses).
- Write module-level functions. Represent data with tensors, tuples, dicts and
  lists. Use closures instead of callable objects.
- Port reference code that uses classes (e.g.
  `~/Area/llmwiki/raw/codes/crown-minimal`) to functions.
- Clean code, PEP 8: lines at most 79 characters, small single-purpose
  functions, descriptive names, a short docstring per public function.
- Comments: use `'''` (not `"""`) for multi-line docstrings, and a plain
  `#` comment for single-line ones.
- DNN models are `nn.Sequential` only, built from the layers in
  `abstraction/lirpa/layer/` (Linear, Conv2d, BatchNorm, Flatten,
  Identity/Dropout, AvgPool2d, MaxPool2d, ReLU, LeakyReLU, Sigmoid, Tanh).
  No ONNX support. The input point keeps the model's input shape.
- Compare bounds with auto_LiRPA (vendored in
  `~/Area/llmwiki/raw/codes/alpha-beta-CROWN/auto_LiRPA`; the pip copy does
  not import) in a scratch script, not in `test/`.

## Coefficient forms

- Coefficients of a symbolic bound are dense matrices, or patches
  (`abstraction/lirpa/layer/patches.py`) when the start node is conv-shaped.
  Use `patches=False` for the dense reference when testing a new layer and
  check equality with `test/test_patches.py`.
- A new conv-shaped layer needs a patch path in `backward`, or it must call
  `patches.as_dense` first.

## Environment

- Python venv: `~/.local/share/venv`. Run Python and tests with
  `~/.local/share/venv/bin/python` / `~/.local/share/venv/bin/pytest`.

## Resource limits

- Machine: AMD Ryzen 9 5900X (12 cores, 24 logical CPUs), ASUS TUF GAMING
  B550-PLUS. At most 23 threads in total (one logical CPU stays free), and at
  most 2 processes in parallel (no `pytest -n`/xdist, no `make -j`, at most 2
  background jobs or subagents).
- Set `OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS` to at most 23
  for every run (the makefiles do) and use `torch.set_num_threads(THREADS)`
  with `THREADS` from `writeup/backend/exp/config.py` in scripts.
- Keep experiments small (small networks, few samples); avoid long loops
  over many seeds.

### History of the CPU fault (read this after a random shutdown or freeze)

- 2026-10-23: heavy parallel load crashed the machine. A thread ramp
  (`python -m writeup.backend.exp.threads`, CSV `writeup/backend/data/threads.csv`) found
  threads 1 to 10 clean and a corrected ECC error in the L1 data cache of
  logical CPU 14 (MC0, load/store unit; sibling thread of CPU 2) at 11
  threads: `mce: [Hardware Error] ... cache level: L1, tx: DATA`. The `Over`
  flag showed that earlier errors had been lost.
- After BIOS changes and a reboot, the ramp ran 10 to 24 threads (all logical
  CPUs) with no machine-check message, and the limit was raised to 23. One
  clean pass of 20 s per level is not proof, because the error is
  intermittent.
- If the machine shuts down, freezes or reboots at random, assume the CPU
  cache-level error is back before debugging the project code:
  1. Check `journalctl -k -b -1 | grep -iE "hardware error|machine check"`
     (the previous boot) and `journalctl -k -b 0` for new lines, and look
     for the CPU number and the cache level (L1/L2).
  2. Lower the limit to 10 threads (the last count that was clean before the
     BIOS change): `THREADS` in `writeup/backend/exp/config.py` and the `*_NUM_THREADS`
     lines in `makefile` and `writeup/makefile`.
  3. Rerun the ramp (`python -m writeup.backend.exp.threads --start 10`; it stops at
     the first machine-check message) to find the new safe level.
  4. In the BIOS (Delete/F2 at power-on) set PBO off and Curve Optimizer to 0,
     or a positive offset on core 2, or update the BIOS; or take CPUs 2 and 14
     offline / avoid them with `taskset -c`; if it persists at stock
     settings the CPU is faulty (warranty).

## Writeup (`writeup/`)

- `writeup/backend/` is the experiment and the plots (Python, run from the
  project root through `writeup/makefile`: `make -C writeup exp plot`).
  `exp/` runs and traces, `plot/` draws; they write the files the site shows.
- `writeup/frontend/` is the explanation website (Hugo, own layouts, no
  theme): `make -C writeup view` serves it, `make -C writeup site` builds it.
  `content/walkthrough.md`, `data/summary.json`, `static/img/` and
  `static/figure/` are generated by the backend: never edit them by hand.
- Raw results stay in `writeup/backend/data/` (CSV per configuration).
- `frontend/static/katex/` is KaTeX's own stylesheet and fonts (vendored, no
  CDN). Hugo renders the math with its embedded KaTeX, so the stylesheet has
  to match that version: if math looks broken after a Hugo upgrade, fetch the
  `katex.min.css` of the newer version (it uses `katex-base`/`katex-strut`
  from 0.18 on) and the 20 `fonts/*.woff2` it names.
- The front page is the **leaderboard** (abstraction + search ranked by solved
  instances, ties by PAR-2): `make -C writeup exp plot` fills
  `frontend/data/summary.json`, which the `leaderboard` shortcode renders.
  The abstractions in the ranking are the tuple `ABSTRACTIONS` of
  `backend/exp/config.py`; adding one there and in `exp/main.py`
  (`bound_fn_of`) is all `make exp` needs.
- Pages: `walkthrough` is generated (`make -C writeup walkthrough`) from
  `backend/exp/toy.py`, which runs the real layer functions; the traces on the
  Search page come from `backend/exp/search_trace.py`.
